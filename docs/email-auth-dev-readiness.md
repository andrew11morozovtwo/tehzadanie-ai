# Фактическая проверка dev перед включением авторизации

> Историческая read-only проверка **до** отдельного разрешения миграции. После неё пользователь разрешил аддитивную dev-миграцию и preview-проверки. Актуальный результат: [email-auth-dev-results.md](email-auth-dev-results.md). Ограничения ниже «не включали» описывают только прежний этап.

Проверка выполнена 2026-11-05. Только SELECT, без вывода строк подключения, паролей, email пользователей или содержимого документов.

## Разделение сред подтверждено

- В приложении используется единственный Pool из `lib/db/src/index.ts`, который читает runtime-managed `DATABASE_URL`.
- Managed dev и production имеют разные логические имена БД, роли и OID. Production проверена только через штатный read-only доступ.
- Дополнительный SELECT через тот же pg-драйвер и окружение, что у preview, совпал с managed dev по имени БД, роли, OID и числу пользователей. Preview не направлен в проверенную production-базу.
- Секреты и строки подключения не выводились, не копировались и не менялись.

## Dev не пустая

| Таблица | Число строк |
|---|---:|
| users | 22 |
| requirement_sessions | 35 |
| messages | 472 |
| project_documents | 30 |
| reference_files | 1 |

Это количества на момент проверки, не разрешение удаления. Перед любым согласованным изменением проверить их заново.

Для аддитивной новой схемы удаление прежних данных само по себе не требуется. Но условие пользователя «если dev пустая» не выполнено, поэтому новую схему и режим не включали. Включение потребует новых таблиц авторизации, нового поля подтверждения, nullable password_hash; первичные подтверждения изменят записи пользователей, а старые preview-JWT перестанут давать доступ в новом режиме.

## Что не выполнялось

Нет DDL, INSERT/UPDATE/DELETE/TRUNCATE, очистки, миграций, перезапусков, реальных писем, изменения окружения, публикации или изменений production. Реальные транзакционные/конкурентные тесты на этой непустой dev не запускались.

## Конкретное решение до дальнейших изменений

Нужно разрешение пользователя, поскольку dev содержит данные:

1. Предпочтительно: отдельная пустая тестовая **схема** внутри dev с отдельными таблицами и явно выбранным search_path для preview. Это не отдельная физическая БД. Существующие public-таблицы и их строки сохраняются; сначала требуется разрешение на этот вариант и подготовка защиты от обращения к public.
2. Либо отдельно разрешённая очистка только dev с пониманием удаления перечисленных данных. Production не является целью очистки.
3. Либо оставить всё как есть.

Пустая схема пока не создана, полная изоляция этого варианта ещё не реализована и не проверена. Разрешение на миграцию пустой БД не считать разрешением тестировать существующие рабочие public-таблицы.

## Resend

Существующее подключение Resend готово к вызову, ключ приложения присутствует. `RESEND_FROM_EMAIL` и `AUTH_PUBLIC_URL` в development не заданы. Пригодность отправителя и доставка не подтверждены; провайдеру письма не отправлялись.

Одно действие владельца: сообщить выбранный адрес отправителя на домене со статусом Verified в Resend — значение для `RESEND_FROM_EMAIL`. API-ключи и строки подключения в чат не присылать. Одна реальная отправка согласуется отдельно.
