# Вход с подтверждением email: комплект внедрения

## Текущий статус

2026-11-05: по отдельному разрешению пользователя аддитивная миграция применена **только к dev**, активная Drizzle-схема обновлена, новый вход включён в preview. Production не менялась. Фактические результаты и ограничения: [email-auth-dev-results.md](email-auth-dev-results.md).

Preview API и frontend перезапущены. Старые preview-JWT больше не дают доступ. Для первой ручной доставки разрешена одна попытка только согласованному получателю в preview: [email-auth-preview-mail.md](email-auth-preview-mail.md). Проверки настоящего PostgreSQL используют только новые синтетические данные и подменённую почту. Production, DNS, ключи, production-сессии, commit/push/merge и post-merge не менялись/не запускались.

Полный перечень фактически изменённых файлов: [email-auth-files.md](email-auth-files.md).

### Что реализовано
- Запрос ссылки без поиска аккаунта и без создания пользователя; единый ответ для новых/старых адресов, лимиты по email и ключевому хешу доверенного IP.
- Токен 256 бит, в БД только SHA-256, срок 15 минут, назначение и состояние доставки. Принятие письма провайдером **не** подтверждает почту.
- HTTP GET сам не погашает токен. При открытии страницы браузер автоматически выполняет один POST, затем переходит в «Мои ТЗ». Токен берётся из фрагмента, убирается из адреса, хранится только в памяти. POST требует точный Origin и host-only double-submit CSRF. Почтовый сканер, выполняющий JavaScript, тоже может погасить ссылку: это ограничение входа без дополнительного клика.
- По последнему явному решению владельца «Только ссылка для всех» старый неподтверждённый аккаунт также входит без пароля. Доступ к его почтовому ящику достаточен для доступа к прежним документам; хеш и ID сохраняются. Автоматического массового подтверждения нет.
- Новый пользователь создаётся только после подтверждения; пароль не генерируется и не отправляется. Старые email, хеши паролей, ID и связи документов не меняются.
- Блокировка отсутствующей строки по email, блокировка токена, условное погашение и создание аккаунта/верификации/сессии в одной транзакции. Подтверждённая ранее дата сохраняется через COALESCE.
- Новый идентификатор `sid` в **существующем** подписанном JWT; в реестре только его хеш. Cookie выдаётся после COMMIT. Сессия на 30 дней, серверный отзыв при выходе, ротация текущей сессии при повторном входе/переключении. `SESSION_SECRET` сохраняется.
- Неподтверждённый старый JWT без серверной сессии не принимается после отдельного включения режима. Владельцы и документы не переназначаются.
- Форма email, таймер, автоматический вход по ссылке, согласие на переключение/отмена, ошибки ссылки и почты; очистка кешей после успешного входа/выхода. Новому аккаунту без имени назначается нейтральное «Пользователь». При ошибке отзыва пользователь не получает ложное сообщение об успешном выходе.
- CSRF для генерируемых и прямых изменяющих запросов только в API текущего приложения. После 403 кеш токена сбрасывается для следующего действия пользователя; изменяющие запросы автоматически не повторяются. Запросы файлов и транскрибации учитывают префикс приложения. Транскрибация в новом режиме требует входа; остальные операции продолжают использовать существующие проверки владельца.
- В production обязателен Verified-отправитель Resend. `onboarding@resend.dev` разрешён исключительно в development-canary для одного получателя и одной попытки. Уведомление разработчику — только после подтверждённой новой регистрации, подавлено в canary; его сбой не отменяет вход.

## Изменения схемы — применены только в dev

Активные `lib/db/src/schema/users.ts`, `src/schema/index.ts` и новый `src/schema/email-auth.ts` соответствуют применённой dev-схеме. `drizzle.config.ts` и post-merge не изменены. Не сливать и не публиковать: это потребует отдельного разрешения и нового штатного production-diff.

| Объект | Изменение | Существующие данные |
|---|---|---|
| users.email | Без изменений, NOT NULL и уникальность сохраняются | Адреса не обнуляются/не нормализуются массово |
| users.password_hash | Снять NOT NULL для будущих passwordless-пользователей | Все прежние значения сохраняются |
| users.email_verified_at | Добавить nullable timestamptz без заполнения | NULL означает отсутствие доказанного подтверждения; существующие достоверные даты не сбрасывать |
| auth_email_challenges | Новая таблица токенов, доставки, сроков, попыток и лимитирования, три индекса | Пользователь до подтверждения не создаётся |
| auth_sessions | Новая таблица хешей sid, владельцев, сроков/отзыва, FK к users и два индекса | Старые аккаунты/документы не удаляются |
| Проекты, документы, файлы, сообщения | Без изменения схемы/владельцев | Сохраняются |

### SQL: два разных материала

1. `docs/email-auth-publish-preview.json` — **исторический снимок до dev-миграции**, когда `hasDiff=false`. Он больше не описывает текущую разницу. Перед любым отдельно разрешённым production-внедрением получить новый штатный read-only diff; старый JSON не применять и не считать отсутствием миграций.
2. `docs/email-auth-schema-review.sql` получен генератором Drizzle и **успешно применён к dev** одной транзакцией с проверкой имени/роли БД и таймаутами. Это не фактический будущий SQL Publish и не ручной production-скрипт. Полный baseline в generated-artifacts не применять: он создаёт весь набор таблиц.

Dev-схема теперь изменена с разрешения пользователя без удаления данных. Перед дальнейшим production-внедрением заново показать штатный diff и получить разрешение. Нельзя запускать Publish только ради SQL, выбирать overwrite data или маскировать офлайн-кандидат под фактический план.

Для Replit-managed production применять схему только штатным Publish после отдельного разрешения. Если выяснится, что опубликованный сервер подключён к внешней PostgreSQL, сначала подтвердить цель и согласовать иной порядок: managed preview не описывает внешнюю базу.

### Блокировки и перерыв

Добавление nullable-поля без default и снятие NOT NULL обычно являются изменением метаданных без переписывания users, но требуют краткой эксклюзивной блокировки. Длительная параллельная транзакция может заставить DDL ждать. Создание FK также требует блокировок; индексы создаются на новых пустых таблицах. Нулевой перерыв и точное время **не измерены и не гарантируются**; запланировать малонагруженное окно и проверить фактический SQL/предупреждения Publish.

У SQL-запросов адаптера лимиты ожидания блокировки 5 секунд и отдельного оператора 10 секунд. Это ограничения запросов приложения, **не гарантия** таймаутов штатной миграции.

## Перед production: резервная копия — обязательный непроверенный пункт

Наличие подходящей точки восстановления этого проекта **не подтверждено**.

1. Откройте **Database → выберите нужную среду → Settings / Data recovery**.
2. Подтвердите точную среду (production или dev с рабочими данными), доступную точку непосредственно перед внедрением и её время/часовой пояс.
3. Подтвердите, что срок хранения покрывает окно внедрения и владелец видит доступный способ восстановления. Наличие пункта меню или обычного checkpoint кода не доказывает пригодность production-backup.
4. Не нажимайте Restore для проверки на работающей базе. Если точки/доступа нет — остановить внедрение и сначала обеспечить резервную копию и понятный порядок восстановления.

В чат достаточно сообщить среду, время точки, окно хранения и доступность восстановления. Не присылайте дампы, рабочие записи, строки подключения или секреты.

## Что указать для почты и ссылок — после согласования

- `AUTH_PUBLIC_URL`: канонический адрес приложения, включая префикс пути, если он есть. Подтверждённый адрес текущей публикации: `https://ai-mieniedzhier-sbora-triebovanii.replit.app/`. Для production не брать адрес preview `.replit.dev`, заголовок Host или произвольный return_to.
- `RESEND_FROM_EMAIL`: **обычный адрес** на принадлежащем вам подтверждённом домене, например `login@your-domain.ru`. Не тестовый resend.dev и не строка с отображаемым именем.
- `RESEND_API_KEY` уже существует; значение не выводилось и не менялось. Наличие ключа не доказывает, что он имеет доступ к выбранному отправителю или что письмо будет доставлено.
- `AUTH_IP_MAX_PER_HOUR`: в dev установлен 60; production не настроен. Учесть пользователей одной сети.
- `AUTH_TRUST_PROXY_HOPS`: в dev установлен 0, то есть заголовку X-Forwarded-For не доверяем. Через общий preview-прокси это может объединять IP-лимит пользователей; production-топология ещё не проверена.
- `EMAIL_AUTH_ENABLED=true` и `VITE_EMAIL_AUTH_ENABLED=true` установлены **только development**. `EMAIL_AUTH_MAIL_MODE=disabled` там явно блокирует настоящие запросы писем с 503 без записи challenge. Отключённый mail mode запрещён вне NODE_ENV=development. Sender и production не настраивались.
- `SESSION_SECRET` не менять: отзыв обеспечивается реестром, а не ротацией общего секрета.

Если в Resend ещё нет подтверждённого домена: в его панели откройте Domains, выберите ваш домен/поддомен, возьмите **реальные записи из панели Resend** и вручную добавьте их у DNS-провайдера. Дождитесь статуса verified, проверьте SPF/DKIM и требуемую политику домена. Не придумывать DNS-значения и не создавать второй SPF вместо корректного объединения записей. Агент домен/DNS/Secrets не менял; статус провайдера и доставка пока не проверены.

## Перед production — только после новых отдельных разрешений

1. Подтвердить фактическую целевую БД, backup/восстановление, отсутствие конфликтующих старых адресов и отправителя. Без этого не внедрять.
2. Отдельно разрешить одну контрольную отправку на собственный адрес пользователя **без включения нового входа**. Убедиться в получении письма, а не только HTTP-успехе Resend.
3. Dev-миграция и активная схема уже согласованы и применены. **Post-merge запускает push:** не сливать задачу и не запускать этот hook; production-миграция при merge не разрешена.
4. Получить настоящий read-only SQL-diff, показать его и предупреждения/блокировки, затем дождаться отдельного разрешения миграции/публикации.
5. Сначала совместимая схема и код при выключенных флагах; потом, в согласованное окно, включить серверный режим и пересобранный frontend. Не допускать frontend on/server off или обратного сочетания.
6. В момент server on старые JWT без зарегистрированного sid перестают давать доступ серверно. Новые записи сессий сохраняются между перезапусками; всех заново при каждом запуске не выкидывает.
7. Выполнить только согласованный ручной сценарий владельца и проверить ошибки. Никаких автоматических/конкурентных тестов, очисток и массовых тестовых пользователей на рабочей базе.

### Контролируемая ручная проверка

Только после разрешений на письмо, миграцию, включение и завершение старых сессий:
- Владелец вводит свой адрес; после запроса новый аккаунт ещё не должен появиться.
- Нажимает ссылку в письме: автоматически открывается «Мои ТЗ», без пароля, обязательного имени и дополнительной кнопки.
- Убеждается, что открылся прежний аккаунт и его документы; данные и токены в чат не копируются.
- Проверяет повторное открытие использованной ссылки и выход. Повторная ссылка требует отдельного разрешения в однократном canary-режиме.
- При проверке другого уже открытого аккаунта отмена не меняет его; переключение требует явного согласия.
- Остановиться при недоставке, ошибке миграции, исчезновении документов, неожиданном аккаунте или обходе подтверждения. Создание второго тестового аккаунта и проверки чужих данных на рабочей базе отдельно не разрешены.

## Откат и ограничения

- **До включения:** оставить оба флага выключенными, остановить выпуск. Аддитивные таблицы/колонку не удалять; старый код совместим с прежними существующими аккаунтами.
- **После включения нельзя просто поставить EMAIL_AUTH_ENABLED=false:** это снова разрешило бы старые подписанные JWT в legacy-режиме. Нельзя откатываться на старую версию авторизации или включать прежний парольный обход.
- Для аварийной остановки новых входов подготовлен `EMAIL_AUTH_LOGIN_PAUSED=true`: email-запросы/подтверждения отвечают 503, но уже выданные подтверждённые сессии и серверный выход работают, старые JWT по-прежнему отклоняются. Этот флаг также требует согласования, сейчас не установлен.
- Предпочтителен совместимый выпуск-исправление с сохранением проверки реестра сессий. Новые passwordless-пользователи имеют NULL password_hash: возврат NOT NULL или старого парольного входа без отдельной совместимости недопустим.
- Восстановление backup заменяет данные и может потерять записи после точки; нужен отдельный план остановки записей, сохранения изменений и согласованного восстановления. Не удалять пользователей/документы и не сбрасывать подтверждения «для отката».

## Что проверено и что не доказано

Прошли **62 офлайн-теста** функций, сервиса, HTTP-маршрутов на Express с хранилищем в памяти, JWT, транзакционного SQL-контракта на подмене клиента и безопасного выключенного режима. Выполнены генерация клиента/Zod, проверки типов и компиляция frontend с включённой UI-веткой в отдельный каталог, без её запуска. Серверный исходник также скомпилирован в отдельный каталог, без выполнения.

Дополнительно прошли **36 новых клиентских проверок** в четырёх конфигурациях: флаг on/off × корень `/`/префикс `/app/`. Это Node-тесты с подменённым fetch и минимальным объектом location, а не настоящий браузер. Проверены отсутствие дополнительных запросов при выключенном флаге, область CSRF-заголовка, наследование заголовков Request, FormData, общий кеш параллельных запросов, обновление после 20 минут, восстановление после ошибки, отсутствие автоматического повтора POST после 403 и безопасные возвраты без двойного префикса.

Команды без подключения к БД/почте:
```sh
# Только клиентские проверки; без запуска приложения и сетевого доступа.
node artifacts/api-server/test/run-email-auth-tests.mjs --client-only
# Полный офлайн-набор: серверные тесты и четыре клиентские конфигурации.
node artifacts/api-server/test/run-email-auth-tests.mjs
```

**Не проверены на PostgreSQL:** исполнение SQL, блокировки/уникальность/откат/конкуренция, распределённые лимиты и сохранность реальных документов. **Не проверены:** сквозной вход браузером с новым режимом, поведение ссылок/StrictMode/мобильных форм в реальном браузере, Resend/DNS/доставка, права ключа на отправителя, фактический маршрут прокси, точка восстановления и будущий SQL Publish. Моки не заменяют эти проверки.
