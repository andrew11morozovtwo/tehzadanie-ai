# Отдельная PostgreSQL-база для тестов входа

**Текущий порядок изменён пользователем:** внешнюю тестовую базу пока не создавать. Эта инструкция — справочная, не разрешение действий и не условие подготовки кода. Реализация адаптера, API и интерфейса уже связана в коде, но выключена. Актуальный статус и порядок внедрения: [email-auth-rollout.md](email-auth-rollout.md).

Рабочий `DATABASE_URL` не использовать для тестов или миграций и не копировать в `TEST_DATABASE_URL`.
Новый вход ещё не включён в работающем приложении. Ниже — прежняя инструкция для возможной будущей подготовки отдельной базы после согласования, а не выполненные действия.

## Вариант: новый пустой проект Neon

1. Откройте [Neon](https://console.neon.tech/) и выберите **Free**. По проверенной 5 ноября 2026 года [странице тарифов](https://neon.com/pricing) это $0 без ограничения срока и без обязательной банковской карты, в пределах бесплатных квот. Платный тариф для небольшой тестовой базы не обязателен. Обычные расходы Replit учитываются отдельно.
2. Выберите **New Project**, название, например `tehzadanie-auth-test`, и PostgreSQL 16. Создайте **новый пустой проект**, не копию/ветку рабочей базы и не импорт рабочих данных. Дополнительные Auth, AI Gateway и другие сервисы для этого не нужны.
3. Убедитесь, что в новом проекте нет пользователей, документов и других рабочих данных. Корневая ветка нового проекта может называться `production` — это название ветки Neon, а не production-база данного приложения; проверьте именно отдельный проект.
4. Нажмите **Connect**, выберите базу и роль **этого тестового проекта**. Для будущих миграций и проверки транзакций выберите прямое подключение, отключив **Connection pooling**. Скопируйте PostgreSQL connection string полностью, включая SSL-параметры. Она содержит пароль — не отправляйте её в чат, README, Git или скриншоты.
5. В текущем проекте Replit откройте **Tools → Secrets** (раздел Setup), затем **New secret**. Ключ: `TEST_DATABASE_URL`; значение: скопированная строка **новой тестовой базы**. Если доступен выбор окружения, выберите Development. **Не редактируйте `DATABASE_URL`, не включайте новый секрет в клиентский код и не меняйте production-настройки.**
6. Сообщите в чате: «Тестовая база создана, TEST_DATABASE_URL добавлен; это отдельная пустая база без рабочих данных, можно продолжать». Само значение не присылайте.

Создавать таблицы вручную или запускать `drizzle-kit push` сейчас не нужно. До применения тестовых миграций требуется проверка назначения подключения. Наличие секрета само по себе не доказывает, что база тестовая; при неоднозначности работа снова останавливается. В будущих тестовых командах запрещён автоматический переход с отсутствующего `TEST_DATABASE_URL` на `DATABASE_URL`.

## Что можно проверить сейчас, без базы

```bash
node artifacts/api-server/test/run-email-auth-tests.mjs
pnpm --filter @workspace/api-server run typecheck
```

Первый запуск проверяет изолированные функции: генерацию и хеширование токена, срок 15 минут, привязку email/назначения, признаки использованного токена, построение ссылки, условия защищённого POST, безопасные возвраты, правила доступа старого аккаунта, согласие на переключение, расчёт лимитов и шаблон письма. Дочернему тестовому процессу не передаются реквизиты баз и почты. Нет подключений к PostgreSQL или отправки писем.

Эти функции пока **не подключены к действующим маршрутам**. Расчёт лимитов — только чистая политика, не готовый распределённый ограничитель; проверка токена не погашает его. Изолированные тесты не подтверждают безопасность ещё не реализованных HTTP-маршрутов.

### Следующий подготовленный слой: сценарии входа

В `artifacts/api-server/src/modules/email-auth/` добавлен сервис с обязательной подстановкой хранилища, отправителя и проверки пароля. Автоматического подключения к БД или Resend нет; активные маршруты и cookies не изменены.

Сервис готовит запрос ссылки без создания пользователя и без поиска существующего аккаунта. Токен хранится только хешем, не становится доступным для подтверждения до принятия письма отправителем и не подтверждает почту самим фактом принятия письма. При подтверждении предусмотрены защищённый POST, проверка имени нового пользователя, действующий пароль старого неподтверждённого аккаунта, ограничение попыток проверки пароля, явное согласие на переключение и повторная проверка срока после медленного сравнения пароля.

Создание/выбор аккаунта, отметка email, погашение токена и запись новой сессии объединены контрактом одной транзакции. Сервис выдаёт случайный идентификатор для поля `jti` **существующего JWT-механизма**, а в хранилище передаёт только его хеш. Подписание JWT и установка cookie должны происходить в будущем HTTP-адаптере после успешного завершения транзакции. Подготовлены проверка срока сессии и серверный отзыв; работающие JWT пока продолжают обслуживаться старой авторизацией.

Тестовый адаптер использует только память процесса и откат снимка состояния. Он проверяет последовательность вызовов, ветвления и поведение сервиса при ошибках, **но не доказывает** PostgreSQL-блокировки, распределённые лимиты, уникальность при реальной конкуренции, HTTP-защиту или изоляцию документов. Для реальной реализации нужны отдельно проверенные блокировки email/IP, блокировки токена и уникальные ограничения БД. Отсутствующий пользователь также должен быть защищён от конкурентного создания по одному адресу.

При подключении к HTTP нельзя брать `currentUserId` и `ipKey` из тела запроса. Идентификатор текущего пользователя берётся из проверенной серверной сессии, ключ IP — из доверенного адреса с учётом разрешённых прокси и серверного ключевого хеша. Cookie CSRF должна защищаться от подстановки поддоменом; параметры cookie, Origin, очистка токена из адреса браузера и очистка пользовательского кеша требуют отдельной интеграционной проверки. Рабочий IP-лимит и процедура ручного восстановления по-прежнему требуют согласования.

На этом этапе прошли 53 офлайн-теста и проверка типов серверного кода. Полной готовности входа это не означает.

## Заблокировано до подготовки отдельной базы

- Применение и проверка миграций, совместимость схемы со старыми аккаунтами.
- Реальное атомарное погашение токена, конкурентные подтверждения, отсутствие дубликатов.
- Устойчивые серверные лимиты по email/IP и конкуренция нескольких экземпляров.
- Создание аккаунта после подтверждения, сохранение документов и проверки изоляции данных.
- Отзыв сессий, отклонение старых JWT, выход и переключение аккаунтов с реальной БД; HTTP-моки уже проверены.
- Интеграционный и браузерный прогон нового входа с подменой почты.

Это блокировка проверок на настоящей БД и ввода в эксплуатацию, а не подготовки связанного кода. PostgreSQL-адаптер, API и UI уже подготовлены, но выключены; HTTP-моки не доказывают корректность настоящей БД. Рабочая авторизация и сессии остаются без изменений.

## Отдельные разрешения

Даже после добавления тестового секрета не разрешены production-миграции, реальная отправка писем, изменения рабочих Secrets/DNS/отправителя, завершение рабочих сессий, публикация, commit и push. Для доставки пользователям нужно отдельно подтвердить пригодность отправителя Resend; тестовый `onboarding@resend.dev` не считать готовым production-отправителем.
