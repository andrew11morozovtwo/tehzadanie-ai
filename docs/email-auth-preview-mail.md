# Отправка ссылок входа в preview

## Текущий режим: Verified-отправитель для всех адресов

Владелец отдельно разрешил отправителя **ТехЗадание.AI <login@notify.databotsolution.ru>** и снятие ограничения одного получателя/одной попытки **только в preview**.

Через подключённый Resend проверен домен `notify.databotsolution.ru`: `verified`, sending `enabled`, click/open tracking выключены. DNS не менялись. Development: `EMAIL_AUTH_MAIL_MODE=preview-verified`, `EMAIL_AUTH_FROM_EMAIL=login@notify.databotsolution.ru`. Остальные sender-настройки не менялись. Доставка использует именно проверенное подключение Resend, без fallback на отдельный прежний API-ключ.

Любой корректный адрес может запросить ссылку через обычную форму. Сохраняются транзакционные лимиты: одно письмо в минуту и пять в час на адрес, IP-лимит 60 в час. Письма ТЗ/аудита, уведомления разработчику и восстановление старых аудитов при старте остаются заблокированы в этом preview-режиме. Production-настройки, сессии и БД не менялись; старый секрет получателя и идентификатор canary не удалялись, но в новом режиме не используются.

Проверки: типы API и 107 офлайн-тестов прошли с подменой отправки. Новые проверки подтверждают разные адреса, лимиты, фиксированного отправителя, использование подключённого Resend, блокировку остальных писем, чужого sender и включения режима в production. Реальное письмо при настройке агент не отправлял: получение в почте ещё нужно проверить вручную.

Ручная проверка: открыть `/login`, ввести собственный действующий email, нажать «Получить ссылку», открыть письмо от указанного отправителя и нажать ссылку — сразу «Мои ТЗ», без пароля и имени. Повторные запросы ограничены обычным таймером и серверными лимитами, а не прежним one-shot permit. Успешное принятие провайдером не означает получение во «Входящих».

## История предыдущей однократной проверки

Ниже зафиксирован прежний canary-этап; его ограничения заменены описанным выше отдельным разрешением.

Получатель предоставлен владельцем через защищённое поле `EMAIL_AUTH_PREVIEW_RECIPIENT`. Значение не переносится в код, документацию, логи или ответы; по пользователям БД адрес не определялся.

Прежнее состояние: **владелец разрешил одну попытку через форму preview**. Использовались `EMAIL_AUTH_MAIL_MODE=preview-canary`, `EMAIL_AUTH_PREVIEW_SEND_APPROVED=true`; фиксированный идентификатор единственной попытки сохранён. Агент письмо не отправлял и форму отправки не вызывал. Production-настройки не менялись.

## Ограничения

- `onboarding@resend.dev` разрешён только для этой development-проверки. `RESEND_FROM_EMAIL`, DNS и домены не менялись.
- Публичный URL должен точно совпадать с текущим `https://REPLIT_DEV_DOMAIN/`; иначе запуск canary-режима отклоняется. Письмо ведёт на `/auth/confirm`, токен находится во фрагменте.
- Единственный допустимый адрес читается сервером из секрета. Чужие адреса блокируются до обращения к repository/provider; имя/наличие существующего аккаунта не проверяются.
- До отдельного согласия обычная форма возвращает явный 503 «Отправка ожидает отдельного подтверждения владельца», не создавая challenge.
- После согласия разрешается **одна попытка отправки через обычную форму**. Резервирование challenge под advisory lock расходует фиксированный permit; параллельные запросы, истечение времени, ошибка провайдера или перезапуск не восстанавливают его. Новая попытка требует нового согласия, а не автоматической смены permit.
- Resend получает стабильный Idempotency-Key для этого permit. Это дополнительная защита, не замена транзакционной квоте.
- Общая граница отправки почты в canary-режиме также запрещает письма ТЗ/уведомления и другие пути без точного разрешённого получателя и auth-permit. Регистрационные уведомления подавлены, восстановление прежних аудитов при старте dev пропускается.
- По последнему решению владельца все аккаунты входят только по ссылке: без пароля, обязательного имени и дополнительной кнопки. Открытие ссылки запускает защищённый POST и переход в «Мои ТЗ»; при уже открытом другом аккаунте переключение требует согласия. Проверять получение письма и вход будет сам владелец.

## Выполненные проверки подготовки

После изменения сценария на «Только ссылка для всех» повторно прошли 104 офлайн-проверки, проверки типов API/frontend и 7 настоящих PostgreSQL/HTTP-проверок на новых синтетических данных с подменой почты. Проверено сохранение ID/хеша специально созданного старого аккаунта при входе без пароля.

Браузер на синтетической ссылке выполнил автоматический вход без полей и кнопки, сохранил сессию после перезагрузки; выход отозвал доступ, повторное открытие ссылки показало ошибку использования. В мобильном размере 390×844 видны email и «Получить ссылку». Проверяющий обнаружил старый заголовок «Ваши проекты» на правильном маршруте; заголовок и навигация исправлены на «Мои ТЗ» только в новом режиме. Этот текстовый фикс проверен кодом/TypeScript без повторного полного браузерного прогона. Реальных писем агент не отправлял; фактическое получение владельцем ещё не подтверждено.

- TypeScript API и 104 offline-проверки с подменённым провайдером: блокировка до согласия; блокировка других адресов; один победитель восьми параллельных запросов; невозможность повтора через два дня/после пересоздания сервиса; расходование permit при ошибке; запрет fallback в production; проверка текущего preview URL; запрет обхода через другой mail-helper; стабильный ключ идемпотентности.
- Синтаксис сохранённого адреса проверен программно, без вывода значения. Это не подтверждает принадлежность аккаунту Resend и не является доказательством доставки.
- Live preview API до согласия возвращает 503; форма `/login` отображается, API запущен.
- Production-флаги сравнены до/после: без изменений. Новые миграции, создание/изменение аккаунтов и реальные вызовы Resend не выполнялись.

## После отдельного согласия

Ровно одна попытка разрешена development-флагом, текущий permit не менять. Владелец вводит в обычную форму **тот же адрес, который сохранил в защищённом поле**, нажимает «Получить ссылку», проверяет входящее письмо/спам и сам открывает ссылку. После открытия автоматически выполняется вход в «Мои ТЗ», без пароля и имени. Успех API Resend не считать получением письма.

При ошибке/неясном исходе не повторять отправку автоматически и не менять permit без согласия. Настройка Verified-отправителя для других пользователей и production остаётся отдельным этапом.
