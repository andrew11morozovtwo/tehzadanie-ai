# ТехЗадание AI

Русскоязычный AI-менеджер требований, который помогает заказчику превратить идею цифрового продукта в понятное техническое задание для разработки.

Пользователь отвечает на вопросы в чате, может записать голосовое сообщение или приложить референсы, а затем получает отдельный структурированный документ в форматах **Markdown** и **JSON**. Готовое ТЗ можно проверить в предпросмотре и отправить разработчику по email.

## Зафиксированное состояние авторизации и публикации

- **Сценарий согласован для всех аккаунтов:** email → «Получить ссылку» → письмо → нажатие ссылки → автоматически «Мои ТЗ». Пароль и обязательное имя не нужны.
- **Dev/preview:** новая схема применена без очистки данных, новый вход включён. Настроена реальная отправка через Resend с подтверждённого домена `notify.databotsolution.ru`; получение писем пользователем подтверждено.
- **Проверено:** проверки типов API и frontend, сборки, 108 офлайн-тестов с подменой почты; ранее — 7 PostgreSQL/HTTP-проверок в отдельной dev-базе и браузерный вход на синтетических данных.
- **Production:** настройки следующего выпуска сохранены, SQL-diff подготовлен. Публикация, применение production-миграции и реальный вход на рабочем сайте **ещё не подтверждены**. Сохранённые настройки не означают, что новая версия уже работает.
- Владелец подтвердил `Recovery window = 7 days`; тестовое восстановление не выполнялось. Перед выпуском нужно проверить доступную актуальную точку восстановления.
- **Следующий шаг:** публикация владельцем через Publish/Republish с проверкой schema-only diff, затем получение письма и вход на рабочем сайте. Не выбирать overwrite data, перенос dev-данных или очистку production.

Точный SQL, настройки, последствия для сессий, ручная проверка и ограничения отката: [комплект production-публикации](docs/email-auth-production-release.md). Эта запись фиксирует результаты подготовки, а не подтверждает завершённый выпуск.

## Зачем нужен проект

На старте продукта важные решения часто остаются в переписке, голосовых сообщениях и разрозненных файлах. «ТехЗадание AI» собирает эту информацию в управляемый процесс:

1. фиксирует идею и контекст проекта;
2. задаёт уточняющие вопросы по пробелам;
3. проверяет, что обязательные темы действительно раскрыты;
4. формирует самостоятельное ТЗ, не копируя в него историю переписки;
5. даёт возможность дополнить проект и собрать новую версию документа.

## Возможности

- создание аккаунта и вход по одноразовой email-ссылке без пароля;
- выход с серверным отзывом сессии; подписанная HTTP-only cookie с идентификатором серверной сессии;
- список проектов и сохранение истории диалогов в PostgreSQL;
- AI-интервью на русском языке с контекстом проекта;
- последовательная проверка обязательных тем:
  - цель и проблема;
  - пользователи и роли;
  - главный пользовательский сценарий;
  - функции первой версии;
  - данные;
  - платформа;
  - интеграции;
  - ограничения;
  - критерий успеха;
- не более 10 обычных вопросов интервью;
- команды «Где ТЗ?» и «Собери ТЗ»;
- отображение прогресса и недостающих блоков;
- запись голосового сообщения с микрофона смартфона или компьютера и транскрибация в редактируемый текст;
- загрузка PDF, TXT, JSON, PNG, JPG и WEBP-файлов размером до 10 МБ;
- генерация ТЗ в Markdown и JSON;
- просмотр текущей версии документа;
- возврат из документа в исходный диалог;
- дополнение уже готового проекта с переводом старой версии в черновик;
- отправка готового ТЗ разработчику через Resend;
- фоновый внутренний аудит качества документа;
- техническое логирование ошибок, предупреждений и медленных запросов без текста диалога и персональных данных.

## Как проходит работа пользователя

1. Пользователь вводит email, нажимает «Получить ссылку», открывает письмо и по ссылке сразу попадает в «Мои ТЗ»; при первом входе аккаунт создаётся автоматически.
2. Создаёт проект и описывает идею в чате.
3. Отвечает на уточняющие вопросы AI-менеджера.
4. При необходимости добавляет голосовые сообщения и файлы-референсы.
5. Видит прогресс сбора требований и список незаполненных тем.
6. Запускает сборку ТЗ после заполнения обязательных блоков.
7. Проверяет Markdown/JSON-документ в предпросмотре.
8. Отправляет финальную версию разработчику или возвращается к диалогу для дополнений.

### Голосовой ввод на смартфоне

В чате можно надиктовать ответ вместо набора текста:

1. Откройте проект и нажмите значок микрофона рядом с пустым полем сообщения.
2. Разрешите браузеру доступ к микрофону и произнесите сообщение.
3. Нажмите на микрофон ещё раз, чтобы остановить запись. Аудио отправится на сервер для транскрибации.
4. Распознанный текст появится в поле сообщения: его можно исправить или дополнить перед отправкой в чат.

Запись работает в браузерах, поддерживающих доступ к микрофону и `MediaRecorder`; для доступа к микрофону нужна защищённая страница (HTTPS). Сообщение **не отправляется в чат автоматически** после распознавания — нажмите кнопку отправки, когда текст готов. Если в поле уже есть текст, вместо микрофона отображается кнопка отправки.

## Проверка отправки ТЗ

Сценарий отправки из Preview проверен в development: кнопка вызывает `POST /api/send-tz`, Resend принимает письмо, а документ получает статус `sent`. Отдельная проверка на тестовом ТЗ подтвердила получение письма в почтовом ящике. Письмо с полноценным ТЗ также было доставлено почтовому серверу, но попало в папку «Спам».

Статус `sent` означает успешную передачу письма почтовому провайдеру, а событие Resend `delivered` — принятие сервером получателя; ни одно из них не гарантирует размещение во «Входящих». Если письмо не видно, проверьте «Спам», фильтры и карантин почтового сервера. Для рабочей отправки используйте подтверждённый домен отправителя: тестовый `onboarding@resend.dev` ограничен адресом владельца аккаунта Resend.

## Архитектура

Проект организован как pnpm-монорепозиторий:

```text
artifacts/
├── api-server/             # Express API, авторизация, AI-логика и email-сценарии
├── requirements-manager/   # React/Vite mobile-first интерфейс
└── mockup-sandbox/         # Изолированный сервер предпросмотра компонентов

lib/
├── api-spec/               # OpenAPI-контракт и генерация схем/хуков
├── api-client-react/       # Сгенерированный React API-клиент
├── api-zod/                # Серверные Zod-схемы
└── db/                     # PostgreSQL-схема и Drizzle ORM
```

Основные точки входа:

- `artifacts/requirements-manager/src/` — страницы и компоненты интерфейса;
- `artifacts/api-server/src/routes/requirements.ts` — API проектов, сообщений, файлов и ТЗ;
- `artifacts/api-server/src/lib/requirements-ai.ts` — состояние интервью, команды и генерация документа;
- `artifacts/api-server/src/modules/ai-audit/` — фоновый аудит качества;
- `lib/api-spec/openapi.yaml` — источник API-контракта;
- `lib/db/src/schema/` — таблицы пользователей, проектов, сообщений, файлов и документов.

## AI-провайдер

Все AI-запросы приложения проходят через **ProxyAPI** с OpenAI-совместимым API:

- `gpt-5.6-luna` — интервью и генерация ТЗ;
- `gpt-4o-mini-transcribe` — распознавание голосовых сообщений;
- `gpt-5.6-terra` — внутренний аудит качества.

Стандартный endpoint:

```text
https://api.proxyapi.ru/openai/v1
```

Ключ ProxyAPI используется только на сервере и не попадает в браузер или клиентский код.

### Проверка полноты ТЗ перед выдачей

Генерация выполняется последовательно:

1. Генератор составляет структурированный черновик по интервью.
2. Независимый AI-инспектор сравнивает черновик с интервью и формирует замечания о пропусках, противоречиях, неподтверждённых добавлениях и непроверяемых критериях.
3. Финальный AI-редактор дорабатывает документ и указывает результат обработки каждого замечания. Отсутствующие ответы заказчика остаются открытыми вопросами, критичные — с явной пометкой.

Это отдельные роли с отдельными инструкциями, использующие ту же модель `gpt-5.6-luna` через ProxyAPI. Обычно выполняются три запроса генерации; при некорректном черновике допускается одна повторная попытка его создания. Инспектор и редактор запускаются по одному разу, без циклических доработок. Тайм-аут черновика — 60 секунд на попытку, инспекции — 60 секунд, редакции — 90 секунд. Дополнительные вызовы увеличивают расходы ProxyAPI и время ожидания.

Документ сохраняется только после успешной проверки структуры всех этапов. Если проверка или редакция завершилась ошибкой, пользователь получает предложение повторить сборку; непроверенный черновик не выдаётся как финальный. Существующий фоновый внутренний аудит остаётся отдельным процессом.

Локальные регрессионные тесты (ответы провайдера подменены, платных AI-запросов нет):

```bash
pnpm --filter @workspace/api-server run test:brief-quality
```

```bash
pnpm install
```

```bash
cp .env.example .env
```

Убедитесь, что задан `DATABASE_URL`, затем примените схему в development-окружении:

API-сервер:

```bash
pnpm --filter @workspace/api-server run dev
```

| Переменная | Назначение |
| --- | --- |
| `EMAIL_AUTH_ENABLED` | Серверный режим входа по ссылке |

| `EMAIL_AUTH_FROM_EMAIL` | Отдельный адрес отправителя писем входа на подтверждённом домене |

Dev и production настраиваются отдельно. Настройки писем входа не заменяют общие настройки отправки документов. В `preview-verified` прочие письма/уведомления отключены. Адреса получателей, API-ключи, строки подключения и одноразовые ссылки в README не записываются.

## Основные API-маршруты

Все маршруты приложения доступны с префиксом `/api`:

```text
GET    /api/auth/email/csrf
POST   /api/auth/email/request
POST   /api/auth/email/inspect
POST   /api/auth/email/confirm
POST   /api/auth/logout
GET    /api/auth/me

GET    /api/sessions
POST   /api/sessions
GET    /api/sessions/:id
POST   /api/sessions/:id/message
POST   /api/sessions/:id/finalize

POST   /api/transcribe
GET    /api/sessions/:id/files
POST   /api/sessions/:id/files
```

В новом режиме старые `POST /api/auth/register` и `POST /api/auth/login` не используются для входа с паролем. Одноразовый токен подтверждается защищённым POST; сама загрузка страницы по GET не погашает его.

Полный контракт находится в [`lib/api-spec/openapi.yaml`](lib/api-spec/openapi.yaml).

После изменения OpenAPI-контракта перегенерируйте клиент и схемы:

```bash
pnpm --filter @workspace/api-spec run codegen
```

## Безопасность и данные

- существующие bcrypt-хеши сохраняются, но в новом режиме пароль для входа не требуется и новым пользователям не генерируется;
- сессия хранится в HTTP-only cookie и проверяется по серверной записи; выход отзывает её;
- AI-ключи доступны только серверу;
- проекты и сообщения изолированы по пользователю;
- логи не должны содержать текст диалога, email и другие персональные данные;
- перед публикацией проверьте production-секреты и не используйте тестовые значения.

### Реализация входа по ссылке и границы изменений

PostgreSQL-адаптер, HTTP API, Resend, формы и серверный отзыв сессий реализованы. Режим выключен по умолчанию; по отдельному разрешению схема применена и новый вход включён в dev/preview. После запроса владельца на публикацию отдельно сохранены production-настройки следующего выпуска. На момент зафиксированной проверки production-миграция не применялась и рабочие данные не менялись; факт выпуска и работоспособность нового входа в production ещё нужно подтвердить.

Текущий сценарий для новых и старых аккаунтов: email → «Получить ссылку» → письмо → нажатие ссылки → автоматически «Мои ТЗ». Пароль и обязательное имя не запрашиваются, существующие ID, имена, хеши и документы сохраняются. Новому аккаунту без имени присваивается нейтральное «Пользователь». Вход выполняет защищённый POST страницы, а не сам HTTP GET; другой уже открытый аккаунт не переключается без согласия. Выполняющий JavaScript почтовый сканер может погасить ссылку: это ограничение автоматического входа без дополнительного подтверждения.

По отдельному разрешению в preview настроен Verified-отправитель Resend для писем входа на любые корректные адреса, с серверными лимитами email/IP. Development-only режим `preview-verified` использует отдельный `EMAIL_AUTH_FROM_EMAIL` и проверенное подключение Resend; прочие письма/уведомления заблокированы. Порядок ручной проверки: [docs/email-auth-preview-mail.md](docs/email-auth-preview-mail.md).

Исходный комплект внедрения, настройки, backup, SQL-ограничения, ручная проверка и откат: [docs/email-auth-rollout.md](docs/email-auth-rollout.md). Текущее состояние подготовки выпуска и точный diff приведены в [docs/email-auth-production-release.md](docs/email-auth-production-release.md). Запрос владельца на публикацию не разрешает commit, push или слияние; эти действия требуют отдельного согласования.

Для отдельно запрошенной владельцем production-публикации подготовлены настройки и фактический штатный SQL-diff: [docs/email-auth-production-release.md](docs/email-auth-production-release.md). Recovery window 7 days подтверждено владельцем; публикацию и миграцию агент не выполнял. Нельзя выбирать overwrite data или перенос тестовых данных. Входные письма используют отдельный sender и `EMAIL_AUTH_TRANSPORT=connector`, без смены остальных почтовых настроек.

Production-базу нельзя использовать для автоматических тестов. Внешнюю тестовую базу сейчас не создаём; [прежняя инструкция](docs/testing-postgresql.md) остаётся только справочной. Настоящие PostgreSQL-проверки разрешены в подтверждённой отдельной dev только на специально созданных синтетических аккаунтах с подменой почты, без изменения прежних записей. Production-изменения по-прежнему требуют подтверждённого backup и отдельного разрешения.

Разрешённая миграция сохраняет аккаунты, адреса, ID, хеши паролей, проекты и документы: добавляет nullable `users.email_verified_at`, снимает NOT NULL с `password_hash`, создаёт `auth_email_challenges` и `auth_sessions` с индексами. Старые адреса не подтверждаются автоматически. После включения нового режима старые сессии без серверного идентификатора перестают давать доступ — всем потребуется войти заново. Нельзя откатывать авторизацию простым выключением `EMAIL_AUTH_ENABLED`: это может снова разрешить старые JWT. При проблеме новых входов используется пауза `EMAIL_AUTH_LOGIN_PAUSED`; порядок восстановления согласуется отдельно.

Клиентские проверки без подключения к приложению, БД и почте:
`node artifacts/api-server/test/run-email-auth-tests.mjs --client-only`.
Без этого аргумента запускается полный офлайн-набор.
